# Як виконувати спеки

Покрокова інструкція для серверного й мобільного розробника: як із готових `spec.md` і `plan.md` отримати код за допомогою GitHub Spec Kit і ШІ-агента.

Правила власності, нумерації й запитів на зміну контракту тут не повторюються — вони в [contracts/WORKFLOW.md](contracts/WORKFLOW.md). Що це за проєкт — у [CONTEXT.md](CONTEXT.md).

Оновлено: 2026-11-11. Команди Spec Kit звірено з репозиторієм `github/spec-kit` на цю дату; перед першим використанням перевірте їх у своїй версії (`specify --help`).

## Коротко

```text
один раз:      розділити репозиторії → встановити Spec Kit → поставити тег контракту
кожна спека:   гілка → вказати Spec Kit папку спеки → прочитати й закрити відкриті питання
               → tasks → analyze → implement → converge → перевірки → pull request
               → рев'ю → злиття → «Перевірка з сервером», коли злито парну спеку
```

Що вже зроблено за вас: для всіх спек MVP написано `spec.md` і `plan.md`. Тому команди `specify` і `plan` для них **не запускаються**: робота починається з `tasks`.

## 1. Один раз: підготовка

### 1.1. Розділити репозиторії

Зараз усе лежить в одному репозиторії. Перед першим рядком коду його розділяють на три, як задумано в [WORKFLOW.md, розділ 8](contracts/WORKFLOW.md):

| Папка зараз | Новий репозиторій | Власник |
|---|---|---|
| `contracts/` | `moye-misto-contracts` | серверний розробник |
| `backend/` | `moye-misto-backend` | серверний розробник |
| `mobile/` | `moye-misto-mobile` | мобільний розробник |

Історію змін кожної папки можна зберегти:

```bash
git subtree split --prefix=backend -b split-backend
```

Потім гілку `split-backend` відправляють у новий порожній репозиторій як `main`. Так само для `mobile` і `contracts`.

Після розділення:

1. У `backend` і `mobile` підключити контракт як підмодуль: `git submodule add <адреса moye-misto-contracts> contracts`.
2. У `moye-misto-contracts` поставити тег першої версії: `git tag v0.1.0`, `git push origin v0.1.0`. Підмодуль у `backend` і `mobile` зафіксувати на цьому тегу.
3. Перевірити посилання: у спеках шляхи до контракту записано як `contracts/...` — після підключення підмодуля вони стануть правильними в обох репозиторіях.

> **⚠ Не вирішено:** куди переходять кореневі `PLAN.md`, `CONTEXT.md` і цей `GUIDE.md`. Пропозиція — у `moye-misto-contracts`, бо його бачать обидва розробники через підмодуль. Рішення за серверним розробником як власником.

### 1.2. Встановити Spec Kit

У кожному з двох репозиторіїв коду (`backend`, `mobile`):

```bash
uv tool install specify-cli
```

```bash
specify init --here --integration <ваш агент>
```

- Точні назви параметрів дивіться в `specify init --help`: у старіших версіях агент задавався параметром `--ai`.
- Після встановлення обов'язково виконати `git diff .specify/memory/constitution.md`. Якщо конституцію перезаписано шаблоном, відновити її: `git checkout -- .specify/memory/constitution.md`.
- Spec Kit знаходить корінь проєкту за папкою `.specify`, а не за git, тому запускати команди треба з кореня репозиторію коду.

### 1.3. Не комітити вказівник на поточну спеку

Spec Kit запам'ятовує, з якою спекою ви працюєте, у файлі `.specify/feature.json`. Він різний у кожній гілці, тож у репозиторії він створить конфлікти. Додайте його в `.gitignore`:

```text
.specify/feature.json
```

`.gitignore` належить спеці-основі (`101` / `201`), тому цей рядок додається в межах тієї спеки.

### 1.4. Налаштувати агента

Spec Kit працює з різними агентами (Claude Code, GitHub Copilot, Cursor, Gemini CLI та інші). Команди викликаються як `/speckit.tasks`; в агентах, де команди встановлюються як навички, назва пишеться через дефіс: `/speckit-tasks`. Далі в тексті — варіант із крапкою.

Щоб агент знав правила проєкту, додайте у файл інструкцій вашого агента (`CLAUDE.md`, `AGENTS.md`, `.github/copilot-instructions.md` тощо) такий блок:

```markdown
Перед будь-якою роботою прочитай:
- CONTEXT.md цього репозиторію і contracts/WORKFLOW.md;
- .specify/memory/constitution.md — обов'язкові принципи;
- spec.md і plan.md поточної спеки, а також файли контракту, на які вони посилаються.

Змінюй лише шляхи з розділу «Шляхи спеки» в plan.md і відведені місця, перелічені там само.
Не змінюй файли в contracts/: якщо в контракті чогось бракує — зупинись і скажи.
Не вигадуй рішень, яких немає в spec.md і plan.md: зупинись і спитай.
```

## 2. Як вибрати наступну спеку

1. Відкрити свій реєстр: [1xx-backend.md](contracts/registry/1xx-backend.md) або [2xx-mobile.md](contracts/registry/2xx-mobile.md). У кінці таблиці MVP — рекомендований порядок.
2. Спека готова до роботи, коли злито всі спеки з колонки «Залежить від». Готовність парної спеки з іншого боку **не потрібна**: мобільна спека працює на прикладах відповідей із `contracts/fixtures/`.
3. Подивитись розділ «Що блокує роботу» в `CONTEXT.md` свого репозиторію. Блокер від замовника зазвичай стосується лише останнього кроку спеки, тож роботу можна почати й без нього.

Можна вести кілька спек паралельно, якщо вони стоять між одними стрілками порядку: їхні «Шляхи спеки» не перетинаються. Як це робити без конфліктів — розділ 6.

Спеки-основи `101` і `201` кожен розробник виконує першими й поодинці: вони створюють спільні файли й перевірку шляхів, на яку спираються всі інші.

## 3. Виконання однієї спеки

Приклад — серверна спека `110-alerts`. Для мобільної все так само, змінюються лише номер і назва.

### Крок 1. Гілка

```bash
git switch main
```

```bash
git pull
```

```bash
git switch -c 110-alerts
```

Назва гілки — точно як назва папки спеки, без `feature/`. За нею автоматична перевірка шляхів (частина спек `101` і `201`) знаходить `plan.md` і перевіряє, що гілка змінила лише свої «Шляхи спеки»; рев'юер теж одразу бачить, яку спеку відкривати. Шпаргалка в `README.md` показує `feature/110-alerts` — у цьому проєкті так не робимо.

### Крок 2. Вказати Spec Kit папку спеки

Spec Kit не визначає спеку за назвою гілки: йому треба сказати, з якою папкою працювати. Найпростіше — записати файл `.specify/feature.json`:

```json
{"feature_directory": "specs/110-alerts"}
```

Інший спосіб — змінна середовища `SPECIFY_FEATURE_DIRECTORY=specs/110-alerts` перед запуском агента; Spec Kit сам запише її у `feature.json`.

> Перемикаючись на іншу спеку, не забудьте змінити цей файл, інакше агент генеруватиме завдання для попередньої.

### Крок 3. Прочитати спеку й закрити відкриті питання

Прочитайте `spec.md` і `plan.md` повністю. Особливо:

- **«Шляхи спеки»** — єдині файли, які можна змінювати, і відведені місця у спільних файлах;
- **«Ризики й відкриті питання»** і дослідження в `plan.md` — їх треба закрити до коду або першими завданнями;
- **версія контракту** на початку `plan.md` — підмодуль `contracts/` має стояти на ній.

Якщо щось незрозуміло чи суперечить контракту:

- уточнення у своїй спеці — правите `spec.md` / `plan.md` самі (це ваші файли) або запускаєте `/speckit.clarify`: агент поставить до п'яти питань і впише відповіді в `spec.md`;
- питання до контракту — мобільний розробник створює файл-запит `contracts/requests/CR-2xx-NN-*.md` (див. WORKFLOW, розділ 4); серверний — змінює контракт сам за правилами версій;
- рішення замовника — записати в `PLAN.md`, розділ відкритих питань, і продовжувати з позначеним припущенням.

### Крок 4. Завдання: `/speckit.tasks`

```text
/speckit.tasks
```

Агент читає `spec.md`, `plan.md` і конституцію й створює `specs/110-alerts/tasks.md`: фази «Підготовка», «Основа», по фазі на кожну історію за пріоритетом, «Завершення». Формат рядка: `- [ ] T012 [P] [US1] Опис із шляхом до файлу`, де `[P]` — можна робити паралельно, `[US1]` — до якої історії належить.

Перевірте `tasks.md` перед роботою:

- кожен шлях у завданнях входить у «Шляхи спеки» або у відведені місця;
- є завдання на кожен пункт розділу «Перевірка» з `plan.md`;
- дослідження з `plan.md` стоять на початку;
- немає завдань із розділу «Поза межами спеки».

Виправте `tasks.md` руками, якщо треба, і закомітьте його окремим комітом.

### Крок 5. Перевірка узгодженості: `/speckit.analyze`

```text
/speckit.analyze
```

Агент нічого не змінює, лише звіряє `spec.md`, `plan.md`, `tasks.md` і конституцію: вимоги без завдань, завдання без вимог, суперечності, порушення принципів. Знайдене виправляєте у своїх файлах. Порушення конституції — це помилка, а не попередження.

### Крок 6. Реалізація: `/speckit.implement`

```text
/speckit.implement
```

Агент виконує завдання з `tasks.md` фаза за фазою й позначає виконані `[x]`.

Рекомендації:

- Просіть агента зупинятися після кожної фази: перегляньте зміни, запустіть тести, закомітьте. Великі зміни без проміжних комітів важко рев'юїти.
- Після кожної фази: `git diff --stat main` — у списку змінених файлів мають бути лише «Шляхи спеки» й відведені місця.
- Перша історія (P1) має запрацювати сама по собі, перш ніж братися за наступну.

### Крок 7. Добивання: `/speckit.converge`

```text
/speckit.converge
```

Агент звіряє написаний код зі спекою й планом і дописує в кінець `tasks.md` нову фазу із завданнями на те, чого бракує або що суперечить спеці. Код і спеку він при цьому не змінює. Далі знову `/speckit.implement` — і так, доки `converge` не скаже, що розбіжностей немає.

### Крок 8. Перевірки перед pull request

| Репозиторій | Що має проходити |
|---|---|
| backend | тести бази й функцій; перевірка відповідей схемами контракту; міграції лише нові, з номером спеки в назві |
| mobile | модульні й віджет-тести; усі сценарії спеки на тестових даних; аналізатор без попереджень |
| contracts | `node tools/check-fixtures.mjs` (якщо змінювався контракт) |

Плюс розділ «Перевірка» з `plan.md` спеки — пройти кожен рядок.

### Крок 9. Pull request, рев'ю, злиття

1. `git push -u origin 110-alerts` і pull request у `main`. В описі: номер спеки, версія контракту, що з розділу «Перевірка» пройдено, що лишилось заблокованим (наприклад, ключ API).
2. Другий розробник читає й лишає **лише коментарі**; у чужу гілку не комітить.
3. Без відповіді два робочі дні — власник може зливати сам (WORKFLOW, розділ 5).
4. Перед злиттям підтягнути `main` у гілку; зливає власник.

### Крок 10. Перевірка з сервером

Коли злито обидві дзеркальні спеки (`110-alerts` і `210-alert-widget`), мобільний розробник перемикає тестову збірку додатку на тестовий сервер і проходить розділ «Перевірка з сервером» своєї `plan.md`. Розбіжність — це або помилка в одній зі спек, або запит на зміну контракту; хто з двох відхилився від контракту, той і виправляє у своєму репозиторії.

## 4. Чого не робити

| Не робіть | Чому |
|---|---|
| `/speckit.specify` для наявної спеки | Створить нову папку з новим номером замість роботи з наявною |
| `/speckit.plan` для наявної спеки | Агент перепише `plan.md`, і зникнуть рішення, «Шляхи спеки» й відведені місця. Якщо план справді треба змінити — правте руками |
| `/speckit.constitution` без домовленості | Конституція спільна для всіх спек репозиторію; зміна — окремим pull request з поясненням |
| Правити файли поза «Шляхами спеки» | Конфлікти з іншими спеками; якщо без цього не обійтись — це зміна плану, її видно в pull request |
| Правити `contracts/` з мобільного боку | Лише нові файли-запити в `contracts/requests/` |
| Редагувати злиту міграцію | Виправлення — нова міграція |
| Комітити ключі, `.env`, `.specify/feature.json` | Ключі — лише в секретах середовищ; вказівник спеки різний у кожного |
| Правити lock-файл руками чи зливати його конфлікт вручну | Версії бібліотек стануть непередбачуваними; lock-файл змінює лише команда (розділ 6) |
| Комітити згенеровані файли (`*.g.dart`, зібрані переклади, типи зі схеми) | Їх змінюють майже всі спеки; вони створюються командою |
| Запускати двох агентів в одній робочій копії | Вони затиратимуть зміни одне одного; для паралельних спек — окремі `git worktree` |
| Перейменовувати функції, які викликає інша спека | Назви на кшталт `private.event_venue_options` записано текстом в іншій спеці; git конфлікту не покаже, а інша спека зламається |

## 5. Нова спека (наступні фази)

1. Номер вибрати зі своєї смуги (WORKFLOW, розділ 2) і додати рядок у свій реєстр.
2. Створити гілку з назвою майбутньої папки (`git switch -c 251-auth`): Spec Kit гілок не створює.
3. `/speckit.specify` з описом і явним номером: агент викликає скрипт створення спеки, якому номер передається параметром `--number 251`, а коротка назва — `--short-name auth`. Якщо номер зайнятий, скрипт візьме наступний вільний і попередить — перевірте назву створеної папки.
4. `/speckit.clarify`, потім `/speckit.plan`. Після `plan` обов'язково дописати в `plan.md` розділи, яких немає в шаблоні Spec Kit, але які вимагає конституція: версію контракту, «Шляхи спеки» з відведеними місцями, «Перевірку з сервером» (для мобільних спек).
5. Рев'ю спеки другим розробником — **до** `tasks` і коду.
6. Далі — як у розділі 3, з кроку 4.

Якщо новій спеці потрібен новий контракт, спершу серверний розробник пише його (`0xx`), ставить тег нової версії, і лише тоді обидві спеки посилаються на цю версію.

### Доповнення до злитої спеки-основи (`101`, `201`)

Буває, що спеці потрібна зміна у файлах `101` чи `201`, для якої немає відведеного місця: новий спільний засіб, правило в `docs/conventions.md`, помічник тестів. Тоді:

1. Зміну **не** роблять у гілці своєї спеки — перевірка шляхів її не пропустить.
2. Створюють гілку з назвою папки спеки-основи (`101-foundation` чи `201-app-shell`); одночасно відкрита лише одна така гілка.
3. Спершу в `plan.md` основи дописують, що й навіщо додається (рядок у «Що ця спека дає іншим спекам» чи нове відведене місце), і завдання в кінець її `tasks.md`; потім код і тести.
4. Доповнення проходить рев'ю й зливається **до** спеки, якій воно потрібне; у плані тієї спеки є посилання на нього.

## 6. Паралельна робота й конфлікти

**Між серверним і мобільним розробником** git-конфліктів майже немає: різні репозиторії, а в `contracts` двоє ніколи не правлять один файл. Розбіжності за змістом (сервер відповідає не так, як у прикладах) знаходить крок «Перевірка з сервером».

**Один розробник, кілька спек одночасно.** Кожна спека — в окремій робочій копії:

```bash
git worktree add ../moye-misto-mobile-221 -b 221-events
```

У кожній копії свій `.specify/feature.json` і свій агент. Після злиття копію прибирають: `git worktree remove ../moye-misto-mobile-221`.

**Де все ж бувають конфлікти і що робити:**

| Де | Чому | Що робити |
|---|---|---|
| Відведені місця (`registrations.dart`, `pubspec.yaml`, `deno.json`, `config.toml`, `admin/package.json`) | Дві гілки додали рядок поруч | Лишити обидва рядки в порядку за алфавітом |
| Lock-файли (`pubspec.lock`, `ios/Podfile.lock`, `deno.lock`, `admin/package-lock.json`) | Обидві гілки додали залежність | Взяти версію з `main` і повторити команду, що його створює (таблиця нижче), потім закомітити |
| Міграції бази | Хтось злив міграцію з пізнішою міткою часу | Перейменувати свою незлиту міграцію на нову мітку (перевірка `101` цього вимагає) |
| Згенеровані файли | Не мають бути в репозиторії | Якщо конфлікт таки є — файл помилково закомічено: видалити його з репозиторію |

Команди для lock-файлів:

| Lock-файл | Команда |
|---|---|
| `pubspec.lock` | `flutter pub get` |
| `ios/Podfile.lock` | `pod install` у папці `ios` |
| `deno.lock` | команда встановлення залежностей Deno з `deno.json` |
| `admin/package-lock.json` | `npm install` у папці `admin` |

Приклад для `pubspec.lock` під час злиття `main` у свою гілку:

```bash
git checkout --theirs pubspec.lock
```

```bash
flutter pub get
```

```bash
git add pubspec.lock
```

(`--theirs` під час `git merge main` означає версію з `main`; під час `git rebase` — навпаки, `--ours`.)

Після кожного `git pull` чи злиття `main` у мобільному репозиторії запускайте `dart run tool/generate.dart`: згенеровані файли не в репозиторії, і без цього код не збереться.

## 7. Типові ситуації

| Ситуація | Що робити |
|---|---|
| Агент генерує завдання для іншої спеки | Перевірити `.specify/feature.json` (крок 2) |
| Агент хоче змінити файл іншої спеки | Зупинити; знайти відведене місце в `plan.md`; якщо його немає — це прогалина в плані, виправити план або домовитися з власником |
| У контракті бракує поля | Мобільний: файл-запит і тимчасовий приклад відповіді у своєму репозиторії. Серверний: зміна контракту з новою версією й записом у `CHANGELOG.md` |
| Спека залежить від незлитої спеки | Не починати або брати іншу між тими самими стрілками порядку |
| Блокер від замовника (ключі, облікові записи) | Робити все, крім останнього кроку; у pull request написати, що лишилось |
| `converge` знову й знову знаходить те саме | Розбіжність, імовірно, у самій спеці: виправити `spec.md` / `plan.md`, а не код |
| Під час роботи з'явилось рішення, якого немає в спеці | Дописати його в `plan.md` («Основні рішення»), щоб рев'юер бачив, чому так |
| Перевірка шляхів не пускає зміну lock-файлу | Гілка змінила lock-файл, не змінивши файл залежностей: агент оновив бібліотеки «заодно». Повернути lock-файл до версії з `main` |
| Після `git pull` код не збирається через відсутні `*.g.dart` | Запустити `dart run tool/generate.dart` |
