# Контекст: contracts

Спільна частина проєкту «Моє Місто»: контракт між сервером і мобільним додатком, реєстри спек і правила асинхронної роботи. Загальний контекст проєкту — у `CONTEXT.md` у корені; продуктовий план — у `PLAN.md`.

Оновлено: 2026-11-11.

## Навіщо ця папка

Двоє розробників працюють паралельно. Контракт — єдине, про що вони мусять домовитись наперед: які функції є на сервері, які параметри вони приймають і що повертають. Додаток працює на прикладах відповідей звідси, доки сервера немає; сервер перевіряє свої відповіді схемами звідси.

## Ключові рішення контракту

- Додаток викликає лише функції бази (RPC); прямого доступу до таблиць немає. Один екран — один запит.
- Усі поля зі схеми присутні завжди; відсутнє значення — `null`.
- Невідоме поле, значення переліку чи посилання додаток пропускає без помилки. Схеми суворі лише для перевірки сервера.
- Час — UTC з суфіксом `Z`; там, де людині треба час міста, сервер дає готові рядки `ГГ:ХВ`.
- Гість розпізнається за ідентифікатором встановлення, який створює додаток.
- Помилка — код HTTP плюс поле `message` з переліку контракту.
- Повідомлення каналу тривоги — лише сигнал; додаток підтверджує його запитом.

## Як змінювати контракт

1. Нове поле, функція чи значення переліку — версія MINOR; зміна чи видалення наявного — MAJOR і лише за згодою мобільного розробника.
2. Змінюється разом: опис у `contract/`, схема в `schemas/`, приклади в `fixtures/`, запис у `CHANGELOG.md`.
3. Перед злиттям:

   ```bash
   node tools/check-fixtures.mjs
   ```

4. Назва прикладу визначає схему: `fixtures/<контракт>/<назва>.<сценарій>.json` перевіряється визначенням `$defs/<назва>` у `schemas/<контракт>.schema.json`.
5. Перевірка розуміє лише ту частину JSON Schema, якою користується контракт, і зупиняється на невідомому ключовому слові: це навмисно.

## Відкриті питання контракту

Зведено в `CHANGELOG.md`. Найважливіші:

1. Чи дає API «Повітряна тривога» тип «розвідувальний БпЛА» (жовтий рівень).
2. Чи повертає Supabase потрібні коди HTTP для помилок (перевіряє спека `101`).
3. Формат файлу офлайн-карти потребує практичної перевірки (`231` → `131`).
4. Постачальник підкладки карти не обраний (`130`).
5. Чи можна закрити канал тривоги для запису стороннім (`110`).

## На що звернути увагу

- Дані в прикладах (назви, адреси, телефони, події) вигадані; перелік черг світла умовний.
- Ідентифікатор Чернігова `7c1f0c5e-6a54-4c0f-9a59-1d6f3a2b0001` сталий і записаний у контракті; не змінювати.
- Реєстри змінюються лише тоді, коли додається спека; стан спек видно з pull request.
