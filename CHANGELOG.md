# Журнал змін контракту

Власник файлу: серверний розробник. Правила версій — у `WORKFLOW.md`, розділ 4.

Кожен запис каже, що змінилось, чи ламає це сумісність і яких спек стосується. Відповіді на запити мобільного розробника (`requests/CR-…`) теж записуються тут.

| `060-reports` | Повідомлення про проблему | `submit_report` |
| `080-analytics` | Події аналітики | `track_events` |

Разом 19 функцій, один канал реального часу, два формати файлів.

### Рішення, закладені в цю версію

- Додаток звертається до сервера лише через серверні функції бази; один екран — один запит.
- Гість розпізнається за ідентифікатором встановлення.
- До кожної відповіді є схема JSON і приклади; відповідність перевіряє `tools/check-fixtures.mjs`.
- Сповіщення в MVP лише про тривогу.
- Повідомлення каналу тривоги — лише сигнал: додаток підтверджує його запитом `get_alert_state` (`010`, правило 5 для додатку). Причина: у відкритий канал може писати не лише сервер. Додано 10.11.2026 під час написання спеки `110-alerts`, до встановлення тегу.

### Уточнення до встановлення тегу (10.11.2026, за підсумком серверних спек)

- `040`: сповіщення про початок надсилається й тоді, коли тривога почалась під час сірого стану; правило «одна тривога — одне сповіщення про початок і одне про відбій» сформульовано через тривогу, а не через перехід «зелений — червоний».
- `080`: строки зберігання розділено: окремі події 90 днів, зведені показники 13 місяців.

### Доповнення до встановлення тегу (11–12.11.2026, за звіркою плану зі спеками й рев'ю завдань)

- `010`, правило 3 для додатку: зелений із кешу не показується ніколи; `red` чи `yellow` із кешу показується, лише поки не минув `stale_after_seconds`, далі сірий. Раніше будь-який стан із кешу був сірим — це суперечило спеці `210`. Сервера не стосується. Рішення 54 у `PLAN.md`.
- `002`, правило 6: дані віджетів із закешованої `get_home` не є свіжою відповіддю й не починають відлік свіжості заново (інакше тривога могла б показати зелений без підтвердження). Спеки `202`, `210`.
- `031`, приклади: розмір, сума й кількість об'єктів `safety_snapshot` в обох описах тепер відповідають файлу `safety_snapshot.default.json` (раніше перевірка суми на тестових даних не проходила); `contracts/.gitattributes` забороняє git змінювати закінчення рядків у цьому файлі.
- `022`, приклади: новий `get_place.private_master.json` — місце з прихованою адресою (потрібен спекам `191`, `222`, `223`).
- `001`, `030`: нове посилання `moyemisto://map?place=<id>` і правило 9 для додатку «Показати на карті» — замість мінікарти на сторінці події чи місця. Нових функцій і полів немає; сервера не стосується. Спеки: `230` (обробник і кнопка), `221`, `222` (відведені місця).

### Відкриті питання цієї версії

Зібрано в розділах «На що звернути увагу» кожного контракту. Найважливіші:

1. Чи дає API «Повітряна тривога» тип «розвідувальний БпЛА» (`010`).
2. Як сервер повертає потрібні коди HTTP для помилок (`001`).
3. Формат файлу офлайн-карти потребує практичної перевірки (`031`).
4. Постачальник тайлів карти не обраний (`030`).
5. Чи може гість читати закритий канал реального часу, у який пише лише сервер (`010`; дослідження R1 спеки `110-alerts`).
