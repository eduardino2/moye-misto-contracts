# Правила асинхронної роботи зі спеками

Документ описує, як два розробники (серверний і мобільний) ведуть spec-driven development у GitHub Spec Kit так, щоб не чекати одне на одного і не отримувати конфліктів при злитті гілок.

Головне правило: **один файл — один власник**. Ніхто не редагує файл, яким володіє інший. Якщо потрібна зміна в чужому файлі, створюється новий файл-запит або коментар у pull request.

## 1. Репозиторії та власники

| Репозиторій | Папка зараз | Що в ньому | Власник |
|---|---|---|---|
| `moye-misto-contracts` | `contracts/` | Спільний контракт між сервером і додатком, приклади відповідей, реєстри спек, ці правила | Серверний розробник (крім файлів, прямо позначених як мобільні) |
| `moye-misto-backend` | `backend/` | Supabase (схема, міграції, серверні функції), сервіс збору даних, адмін-панель, спеки `1xx` | Серверний розробник |
| `moye-misto-mobile` | `mobile/` | Flutter-додаток, спеки `2xx` | Мобільний розробник |

Обидва репозиторії коду підключають `moye-misto-contracts` як git submodule у папку `contracts/` і фіксують конкретну версію (тег).

## 2. Нумерація

| Діапазон | Що це | Де лежить | Хто створює й редагує |
|---|---|---|---|
| `0xx` | Контракт | `moye-misto-contracts/contract/0xx-name.md` | Серверний розробник |
| `1xx` | Спека сервера | `moye-misto-backend/specs/1xx-name/` | Серверний розробник |
| `2xx` | Спека додатку | `moye-misto-mobile/specs/2xx-name/` | Мобільний розробник |

- Останні дві цифри однакові для однієї функції: контракт `010-alerts`, серверна спека `110-alerts`, мобільна спека `210-alert-widget`.
- Якщо функція існує лише з одного боку, парного номера просто немає (наприклад `170-admin-panel` без `270`).
- Смуги останніх двох цифр зарезервовано за темами, щоб нові спеки наступних фаз не ламали порядок:

| Смуга | Тема |
|---|---|
| 00–09 | Основа проєкту, головна сторінка |
| 10–19 | Тривога, світло |
| 20–29 | Каталог: категорії, події, місця, сервіси |
| 30–39 | Карта, офлайн |
| 40–49 | Push-сповіщення |
| 50–59 | Кабінет, акаунт, адреса, збережене |
| 60–69 | Скарги на дані, партнери, просування |
| 70–79 | Адмін-панель, «Громада» |
| 80–89 | Аналітика, лояльність |
| 90–99 | Випуск, соціальна частина |

- Коли смуга закінчиться, сервер продовжує в діапазоні `3xx`, додаток у `4xx` з тими самими смугами.
- Нову спеку створює лише її власник командою Spec Kit із явним номером, наприклад: `create-new-feature.sh --number 112 --short-name "power-auto-import" "опис"`. Без `--number` Spec Kit сам візьме наступний номер після найбільшого в папці `specs` цього репозиторію.
- Перед створенням нової спеки власник додає рядок у свій реєстр (`registry/1xx-backend.md` або `registry/2xx-mobile.md`).

## 3. Хто що редагує

| Шлях | Власник | Що може інший розробник |
|---|---|---|
| `contracts/contract/0xx-*.md` | Серверний | Читати; просити зміну файлом-запитом |
| `contracts/schemas/**` | Серверний | Читати; генерувати з них моделі за бажанням |
| `contracts/fixtures/**` | Серверний | Читати й використовувати як тестові дані |
| `contracts/tools/**` | Серверний | Запускати |
| `contracts/CHANGELOG.md` | Серверний | Читати |
| `contracts/registry/1xx-backend.md` | Серверний | Читати |
| `contracts/registry/2xx-mobile.md` | Мобільний | Читати |
| `contracts/requests/CR-2xx-NN-*.md` | Мобільний (лише створює нові файли) | Серверний відповідає окремим файлом або записом у `CHANGELOG.md` |
| `contracts/requests/CR-2xx-NN-*.answer.md` | Серверний | Читати |
| `contracts/WORKFLOW.md`, `contracts/README.md` | Серверний | Пропонувати зміни коментарем у pull request |
| `backend/**` | Серверний | Читати; рев'ю лише коментарями |
| `mobile/**` | Мобільний | Читати; рев'ю лише коментарями |

У спільному репозиторії `contracts` двоє ніколи не правлять один файл: мобільний розробник лише додає нові файли у `requests/` і веде свій реєстр. Тому конфлікт при злитті там можливий тільки в разі порушення цієї таблиці.

## 4. Контракт

- Контракт — єдине джерело правди про схему даних, запити, відповіді, канали реального часу, push і коди помилок. Спеки `1xx` і `2xx` посилаються на нього за номером і версією, а не копіюють його.
- **Версії.** Репозиторій `contracts` має теги `vMAJOR.MINOR.PATCH`. Нове необов'язкове поле чи новий запит — це MINOR. Зміна або видалення наявного — MAJOR, і вона можлива лише після запиту й згоди мобільного розробника. Кожна зміна записується в `CHANGELOG.md` з номером контракту і, якщо була, номером запиту.
- **Фіксація версії.** У `plan.md` кожної спеки вказано версію контракту, під яку вона написана. Оновлення submodule до нової версії — окремий маленький коміт власника репозиторію коду.
- **Схеми й приклади відповідей.** Для кожної відповіді в `contracts/schemas/` є схема JSON, а в `contracts/fixtures/` — приклади для різних сценаріїв. Мобільний розробник будує на прикладах тестові джерела даних і не чекає готового сервера. Серверний розробник перевіряє тестами, що реальні відповіді проходять ті самі схеми. Відповідність прикладів схемам перевіряє `node tools/check-fixtures.mjs`; без цієї перевірки зміни в репозиторій контракту не зливаються.
- **Запит на зміну.** Мобільний розробник створює файл `requests/CR-<номер своєї спеки>-<порядковий номер>-<коротка назва>.md`, наприклад `CR-221-01-event-age-limit.md`. У файлі: що потрібно, навіщо, який приклад відповіді очікується, чи блокує це роботу. Серверний розробник або змінює контракт (і вказує номер запиту в `CHANGELOG.md`), або відмовляє файлом `CR-221-01-event-age-limit.answer.md` з поясненням.
- Поки запит не виконано, мобільний розробник працює з власним тимчасовим прикладом відповіді у своєму репозиторії й позначає це в спеці як відкритий пункт.

## 5. Життєвий цикл спеки

1. **Гілка.** Одна спека — одна гілка з тією самою назвою, що й папка спеки (`110-alerts`), — один pull request.
2. **Файли.** У папці спеки лежать `spec.md` (сценарії, вимоги, критерії приймання) і `plan.md` (технічне рішення, версія контракту, перелік шляхів, якими володіє спека). Початкові `spec.md` і `plan.md` для MVP уже написані. `tasks.md` власник генерує командою Spec Kit безпосередньо перед початком роботи.
3. **Рев'ю спеки.** Інший розробник читає `spec.md` і `plan.md` та лишає коментарі в pull request. Він не комітить у чужу гілку й не редагує чужі файли. Правки вносить власник.
4. **Мовчання.** Якщо рев'юер не відповів за два робочі дні, власник може зливати спеку без його схвалення (припущення; змініть термін за потреби).
5. **Реалізація.** Власник виконує завдання у своїй гілці. Код торкається лише шляхів, перелічених у розділі «Шляхи спеки» її `plan.md`.
6. **Злиття.** Гілку зливає її власник у `main` свого репозиторію. Перед злиттям він підтягує `main` у гілку.
7. **Перевірка пари.** Коли злито обидві дзеркальні спеки (наприклад `110` і `210`), мобільний розробник перемикає додаток із тестових даних на справжній сервер і проходить розділ «Перевірка з сервером» своєї спеки. Знайдені розбіжності оформлюються запитом на зміну або виправленням у тій спеці, яка відхилилась від контракту.

## 6. Як не чекати одне на одного

- Контракт пишеться першим. Після цього серверна й мобільна спеки з однаковими останніми цифрами виконуються паралельно в будь-якому порядку.
- Мобільна спека залежить лише від версії контракту та прикладів відповідей, а не від готовності серверної спеки.
- Серверна спека залежить лише від контракту, а не від додатку.
- Порядок усередині кожного репозиторію задає реєстр спек (колонка «Залежить від»).

## 7. Правила всередині одного репозиторію

Конфлікти між власними гілками одного розробника теж можливі, якщо дві спеки правлять один файл. Тому:

- Кожна спека перелічує у `plan.md` шляхи, якими володіє. Дві незлиті спеки не мають спільних шляхів.
- Спільні файли (точка входу, навігація, залежності, локалізація, спільні серверні модулі) належать спеці-основі (`101`, `201`). Інші спеки додають у них лише свій рядок чи блок у відведеному місці; деталі — у конституціях `backend/.specify/memory/constitution.md` і `mobile/.specify/memory/constitution.md`.
- Міграції бази мають назву з часовою міткою й номером спеки. Злиту міграцію ніхто не редагує; виправлення — це нова міграція.

## 8. Перше налаштування

1. Створити три репозиторії та покласти в них вміст папок `contracts`, `backend`, `mobile`.
2. У `backend` і `mobile` підключити контракт: `git submodule add <адреса moye-misto-contracts> contracts`.
3. У `backend` і `mobile` встановити Spec Kit (`specify init --here`). Після цього перевірити через `git diff`, що файл `.specify/memory/constitution.md` не перезаписано шаблоном; якщо перезаписано, відновити його з коміту.
4. Перевірити, що у встановленій версії Spec Kit скрипт створення спеки підтримує параметр `--number` (він є в актуальній версії на момент написання, 10.11.2026).
5. Поставити першу версію контракту: тег `v0.1.0`.

## 9. Типові ситуації

| Ситуація | Що робити |
|---|---|
| Додатку потрібне нове поле у відповіді | Мобільний створює файл-запит у `contracts/requests/`; до відповіді працює з тимчасовим прикладом |
| Серверний розробник хоче змінити наявне поле | Пише про це в pull request до `contracts`; зливає лише після згоди мобільного; версія MAJOR |
| Знайдено помилку в чужій спеці | Коментар у pull request або issue в репозиторії власника; чужий файл не редагується |
| Контракт двозначний | Мобільний створює файл-запит із типом «уточнення»; серверний уточнює текст контракту (PATCH) |
| Потрібна нова спека поза переліком | Власник додає рядок у свій реєстр, створює спеку з номером зі своєї смуги |
| Треба змінити ці правила | Pull request до `WORKFLOW.md` від серверного розробника після згоди обох |
